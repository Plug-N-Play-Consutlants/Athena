# v0.7.10.67.27 — Fantrax Period Contract Differential Investigation

The accepted v67.26 consolidated Developer Diagnostics entry is unchanged. Studio's existing **Fantrax Diagnostics → Player-period contract → Run Probe** now makes two additional, bounded, read-only `getPlayerStats` candidate requests for the selected period and an adjacent negative-control period.

The candidate fields `seasonOrProjection`, `timeframeTypeCode`, `transactionPeriod`, and `timeStartType` were observed in the publicly available `downloadPlayerStats` request used by https://github.com/sprx97/FantraxCapfriendly/blob/main/fantrax.py . That export endpoint is **not equivalent** to `fxpa/req` `getPlayerStats`. Accordingly this is a strictly provisional differential experiment, not a verified request contract. No cookies, credentials, player rows, IDs, or raw response values are persisted. A short hash of the anonymous distribution of FPts scalar values is used to tell whether the two returned data sets differ; unchanged results can mean these request fields are ignored. Results differ can also have causes other than the intended scoring-week filter.

The probe continues to return `period_identity_unverified` and refuses scoring-ledger writes even if two responses differ. A verified exact-period request and response, plus roster-credit semantics, remain necessary before Athena may assign individual contributions. Any provider errors are recorded only as safe exception class names. No new permanent Studio buttons were added.

**Live validation:** open Developer Mode → Fantrax Diagnostics → Player-period contract, enter season 2026, period 8, run the diagnostic, and inspect `candidate_contract` in the report. `credit_eligible` must remain false. Test both the case where responses differ and where no difference is detectable before deciding whether this provisional contract is useful.
