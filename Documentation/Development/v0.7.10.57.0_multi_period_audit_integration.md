# AthenaEngine 0.7.10.57.0 — Multi-Period Audit Integration & Sync Diagnostics

**Status:** Local integration PASS (124 pytest tests + 36 unittest subtests). **Live Studio acceptance pending.**

**Installation:** Extract the scoped ZIP over an existing **0.7.10.56.0** repository. Archive paths begin with `AthenaEngine/`, so extract in the parent directory of the existing repository (`F:\Development\`) or copy the contents inside that folder. Do not create a nested `AthenaEngine/AthenaEngine` folder.

## Scope

1. **Multi-period request recognition.** `Weeks 2 and 3`, `Week 2 and Week 3`, `Periods 2, 3 and 4`, and bounded `Week 2 through Week 4` preserve *all* explicit periods (up to eight). Single-week and date-window inquiries retain their previous behavior. Week 3 remains the editorial lead in a Weeks 2–3 report.
2. **Athena owns every requested audit.** For a multi-period reconciliation inquiry, Athena invokes its established historical scoring audit for **each requested period**, archives individual periods under `Output/PeriodScoringAudit/<league>/<season>/period_NNN.json`, and builds a source-constrained period-by-period research result. The implementation has no player/team hardcodes and cannot manufacture unverified standings, missing player credits, or future scoring periods.
3. **Request manifest separate from sync.** `request_manifest.json` documents Scout-triggered auditing without overwriting `sync_manifest.json`. Each includes team reconciliation counts, unresolved ACTIVE identities, scoring differences, and explicit unavailable-source reasons.
4. **Scout audit presentation.** An explicit multi-period request now receives separate team-level rows for *every requested week*, with official Fantrax totals vs identified NHL ACTIVE scoring, identity gaps, and excluded reserve production. A missing week appears as an error, not silently replaced by the latest week. The Week 3 editorial narrative remains available without a duplicate 14-team scoring table.
5. **Self-explaining debug export.** A new **Historical Scoring Audit** section in the normal **TXT and JSON** debug export includes sync-stage status (optional stage passed / warned / skipped), per-period results for sync and explicit Scout requests, identity-coverage diagnostics and source failure reasons. Malformed/missing manifests no longer crash the export.

## Evidence semantics

- `13/14` is numerical team-total agreement, **not** independent evidence of game-effective Fantrax eligibility.
- Unidentified ACTIVE skaters remain explicit source exceptions; neither zero scoring nor a guessed NHL player link is assumed.
- RESERVE and INJURED_RESERVE NHL G+A are excluded from calculated ACTIVE scoring even if those players scored in NHL games.
- Period 1 needs an independently supplied prior baseline or a different verified method; it is not silently calculated from season standings.
- This build does not claim to have eliminated Waterbury's remaining two points; a live audited period may continue to show 36 vs 38.

## Acceptance in Studio

Run **Reload Build → Verify → Sync League**, then in Scout ask:

> Reconcile the JHLPAA scoring for Weeks 2 and 3. Show each week's team-by-team Fantrax totals against NHL ACTIVE production, list unresolved ACTIVE identities, scoring differences, and excluded reserve points. Explain any unavailable source for either week, then deliver the Week 3 editorial recap using verified evidence.

Save the **new Scout TXT debug export** and session log. Verify that (1) *Historical Scoring Audit* appears and contains separate *Sync* and *Scout request* entries, (2) Weeks **2 and 3 each appear with their own outcome** or explicit unavailable reason, (3) Justin remains 30/30 and Waterbury's discrepancy is not suppressed, and (4) no bench points are credited or fabricated.

**Interpretation:** If the sync audit shows Week 2 unavailable, that is upstream evidence/acquisition, not merely a Scout presentation issue. If both manifest periods are audited but the report omits Week 2, that is routing/composition. This overlay enables us to diagnose the distinction from the exported logs without manually requesting internal artifacts.
